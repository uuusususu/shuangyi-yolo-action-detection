## Context

检测开启后，`_resolve_display_source()` 返回 `worker.get_display_frame()`（推理所用的那一帧），`_should_draw_runtime_overlay()` 要求 `overlay.source_frame_id == frame_id` 才绘制。因此主画面与检测框严格同帧——这是现场明确要求保留的语义，代价是主画面的延迟与刷新率都等于一个推理周期。

排查发现“框在后面追”有两个彼此独立的成因，都与推理算力无关：

**事件积压。** `_inference_loop` 每完成一帧就 `overlay_state_updated.emit(...)`，接收方在主线程，Qt 采用排队投递，且没有任何丢弃或合并机制。界面处理一个事件的耗时一旦超过推理一帧的耗时，队列就单调增长，界面持续处理队列头部越来越旧的帧，延迟随运行时间累积且不会自行恢复。推理线程自身已经正确实现了“只吃最新帧、丢弃中间帧”（`fid <= _last_inferred_frame_id` 即跳过），但这个原则没有延伸到界面侧。

**与新数据无关的重复渲染。** `_display_timer` 以固定周期持续触发 `_update_display()`，检测开启时也不停止。两次推理之间待显示帧与检测结果均未变化，却会重新拷贝、重画、重做色彩转换与缩放，产生逐像素完全相同的结果。渲染频率因此挂钩于界面刷新频率而非新数据到达频率。

两者会相互放大：渲染越慢，队列积压越严重；队列里每个事件又各自触发一次完整渲染。

关于分辨率的定位：上述开销的绝对量随相机分辨率线性放大，当前 2000 万像素相机（单帧 BGR 约 60MB）使其尤为突出，但**它们在任何分辨率下都是净浪费，本设计不以某一特定分辨率为前提**。反向的事实是，ONNX 推理输入固定为 640×640，其耗时与相机分辨率无关（实测约 41ms）；因此后续更换低像素相机后，本设计各项优化依然成立，只是绝对收益下降，而推理耗时会重新成为主导项——届时最值钱的将是会话调优而非渲染优化。

约束：

- 判定链路（ROI 引擎、步骤引擎、统计、声音、证据图）不得有任何行为变化。
- 模板匹配的得分、位姿与匹配结论不得变化，不接受“分数接近”。
- 不引入新依赖，不改动模型，不改变检测输入的生成方式。

## Goals / Non-Goals

**Goals:**

- 让显示延迟不随运行时间累积。
- 保持并以规格固化“检测中主画面 = 推理同帧，只叠加同帧框”，并消除停止检测后的框漂移窗口。
- 让渲染频率挂钩于新数据到达频率，而非界面刷新频率。
- 把完整分辨率整图操作的次数降到必要下限。
- 消除模板匹配中与画面无关或可复用的重复计算。
- 让 ONNX 在低配 CPU 现场可按机器调优会话线程与图优化级别。
- 让仅对特定推理后端有效的参数不再误导现场。
- 让“周期慢在哪一段”可被现场直接读出。

**Non-Goals:**

- 不改判定逻辑与任何 PASS/NG 结论。
- 不改显示语义：不做“最新预览帧 + 过期框”，也不做运动外推。
- 不更换 ONNX 执行提供器，不引入 DirectML/OpenVINO/CUDA 等新依赖。
- 不做模型层面的改动：不量化、不更换更小模型、不调整推理输入尺寸。
- **不改变检测输入的降采样插值方式**。当前 `_preprocess()` 使用 `INTER_LINEAR` 做大比例降采样，存在混叠导致小目标细节丢失的风险，`INTER_AREA` 是降采样的正确选择；但该改动会改变检测结果，必须与精度对比验证一起单独评估，不能混入本次的等价优化。更换低像素相机后降采样倍数减小，届时再评估。
- 不调整相机 SDK 的输出分辨率、缓冲深度与触发模式。

## Decisions

### D1：把渲染从事件处理路径中解耦，而不是直接丢弃积压事件

“只处理最新事件、丢弃积压”这个直觉方案**不能直接采用**，因为 `_on_overlay_updated` 同时承担两件事：判定（ROI 引擎与步骤引擎的状态推进、统计、声音、证据）和显示。ROI 引擎依赖每一个被推理帧累积 PASS/FAIL 稳定帧计数，丢弃事件会改变稳定帧的累积速度，进而改变判定时序——这违反“判定链路不得有任何行为变化”的约束。而推理线程本就已经在丢帧，判定的输入序列已经稀疏，界面侧再丢会进一步失真。

**决定**：拆开这两件事的触发路径。

- 事件处理**只做判定**并更新“当前应显示的内容”状态，不再在末尾直接调用 `_update_display()`。
- 渲染由定时器统一驱动，每次取当前最新状态渲染。

这样每个被推理帧的判定一个不少，而渲染次数与积压事件数量脱钩：无论队列里排了多少事件，渲染都只按定时器节奏进行且总是反映最新内容。原先“每个积压事件各自触发一次完整渲染”的放大效应被直接消除，这也正是队列得以追上的关键——积压的根因是渲染太慢，把渲染移出事件处理路径后，事件处理本身变得廉价。

**备选方案**：在 worker 端做背压，上一个事件未被处理前不再投递。**未采用**，这等价于在界面侧丢帧，同样会改变判定输入序列；且会让推理线程阻塞在界面进度上。

**遗留约束**：事件负载中携带的整帧快照用于 NG 同帧证据，必须逐事件保留，不能改为按帧号回查（后续推理会覆盖 worker 的显示帧槽位，回查将拿不到对应帧）。因此瞬时积压期间内存仍会上升。本设计接受这一点，因为解耦后事件处理变廉价、积压窗口很短；若后续实测显示仍有持续积压，再单独评估负载瘦身。

### D2：用渲染守卫消除重复渲染，且同时覆盖检测与预览

定时器驱动渲染后，仍需避免在内容未变时空转。

**决定**：在 `_update_display()` 内加渲染守卫——若本次的（待显示帧编号，检测结果帧编号，显示控件尺寸）与上次已渲染的完全一致，则直接返回。

**守卫必须同时覆盖预览状态**。工业相机的实际帧率通常低于界面刷新频率，因此预览时定时器同样在对同一张相机帧反复渲染。预览路径的帧编号取自已有的 `get_latest_preview_frame_id()`，语义完整，无需新增测量点。“持续显示最新帧”与“同一帧只渲染一次”并不冲突——帧编号一变化就立即渲染。

控件尺寸纳入守卫键，保证窗口缩放后能立即重绘。

守卫与 D1 相互配合：D1 保证渲染次数不随积压增长，D2 保证渲染次数不随定时器空转增长。

### D3：停止检测后立即停止绘制检测框

`_should_draw_runtime_overlay()` 在 `inference_on` 为假时走 `_overlay_is_fresh()` 分支，只要距上次检测不超过 `display_result_max_age_ms` 就继续绘制；而此时 `_resolve_display_source()` 返回的已是不断刷新的最新预览帧。结果是最后一批检测框被叠加到新画面上，目标一动即错位——这正是“框必须严格贴在对应像素上”所要排除的情形，只是窗口较短。

**决定**：停止检测后立即不再绘制检测框。预览状态下主画面只显示最新相机帧本身（以及与画面无关的 ROI 矩形等静态叠加）。

`display_result_max_age_ms` 随之失去作用对象，保留配置项但不再参与绘制判断，避免破坏既有配置文件的兼容性。

**备选方案**：停止检测后连同画面一起冻结在最后一帧。**未采用**，停止检测后操作员通常需要继续观察工位实况，冻结画面会妨碍这一用途。

### D4：缩放在色彩转换与图像构造之前完成

当前顺序是：全分辨率画框 → 全分辨率 `cvtColor` → `QImage` → `QPixmap` → `SmoothTransformation` 缩放。最重的三步全部作用在完整分辨率数据上，而最终只需要显示控件尺寸的那一小块。

**决定**：改为先用 `cv2.resize` 把画好框的帧按 `KeepAspectRatio` 缩到控件尺寸，再对小图做 `cvtColor` 与 Qt 图像构造，去掉 `QPixmap.scaled`。缩小用 `INTER_AREA`，放大用 `INTER_LINEAR`。

此处选用 `INTER_AREA` 与 Non-Goals 中“不改变检测输入插值方式”并不矛盾：这条路径只影响给人看的画面，不进入任何判定。

选 OpenCV 而非 Qt 做缩放，除了作用在更小数据量上，还因为 OpenCV 的缩放会释放 GIL，不会阻塞采集与推理线程。

检测框仍在**完整分辨率帧**上绘制后再缩放，以保证框与画面像素严格对应；不改为“先缩放再按比例画框”，避免在缩放取整上引入与同帧语义无关的偏差。绘制本身只触及少量像素，不构成开销。

### D5：采集链路上的两次整图拷贝合并为共享只读快照

`MvSdkCamera.read()` 末尾已返回一个新数组，采集线程独占；灰度相机分支的 `cvtColor` 同样产出新数组。此后 `_capture_loop` 又分别为预览槽位和推理槽位各拷贝一次。

**决定**：两个槽位指向同一份只读快照，取消这两次拷贝。配套约束写入规格：帧缓冲的消费者不得原地修改这些数组；`get_latest_preview_frame()` 继续返回副本；推理线程交给界面前的那次拷贝**保留**，因为界面要在其上原地画框。

### D6：模板匹配做等价优化，不改变数学定义

按收益排序：

1. **搜索窗口先裁剪再灰度化**（收益最大）。`find()` 当前对整幅画面做 `cvtColor` 后才裁出搜索窗口，而搜索 ROI 通常只占画面一小部分。**决定**：先按搜索 ROI 裁剪再灰度化。灰度化是逐像素运算，裁剪后逐像素结果不变。`_as_gray` 原本承担的通道合法性校验需以显式校验保留在裁剪之前，以免非法输入的报错时机被推迟。

2. **静态量每帧重算**。`rotated_bbox(0)` 遍历全部角度候选并逐个旋转层 0 点集，但它只依赖模型点集与角度设置。`find()` 每帧调用它两次——一次直接调用，一次经由 `min_search_size(0)`。`ShapeModelSettings` 是 frozen，`_levels` 是 tuple，`with_settings()` 返回新实例，因此结果在实例生命周期内恒定，**可安全缓存**。

3. **细化阶段重复旋转同一点集**。`_refine()` 对每个候选、每个候选角度做 5×5 平移搜索，而 `_score_at()` 每次调用内部都重新旋转一遍点集与方向——同一角度被旋转 25 次。`_subpixel()` 的 3×3 网格同理，同一角度旋转 9 次。**决定**：拆出按已知位姿评分的内部函数，调用方每个角度只旋转一次。

4. **双线性采样索引重复计算**。`nx` 与 `ny` 两个梯度场使用完全相同的采样坐标，当前各自独立计算下标、边界裁剪与插值权重。**决定**：合并为一次坐标与权重计算、两次加权采样。

此外 `_angle_curve()` 计算的角度响应曲线只服务于诊断记录，生产判定不读它。**决定**：仅在诊断会话激活时计算，由调用方传入激活状态。

**等价性验证方式**：对固定图像与模板，优化前后的匹配得分差必须小于 `1e-6`，位姿与 `matched` 结论必须完全一致。仅第 4 项因浮点结合律变化可能产生该量级差异，其余各项为纯缓存、裁剪顺序与调用顺序变化。不接受以“分数接近”作为放行标准。

### D7：ONNX 会话线程与图优化级别显式可配置

`create_yolo_processor()` 构造 `OnnxObbProcessor` 时未设置 `SessionOptions`，因此 CPU 线程数与图优化级别只能吃默认值。ONNX Runtime 默认会占用全部核心，与采集线程、界面线程争抢，在核心数少的机器上反而可能拖慢整体。

**决定**：新增 intra-op 线程数（0 表示交给运行时决定）与图优化级别两项配置，经 `create_yolo_processor()` 传入，并复用现有“保存即生效”的处理器重建路径。

执行提供器保持现状不做配置化。现场 onnxruntime 只提供 `CPUExecutionProvider`，暴露一个没有可选值的配置项没有意义；更换执行提供器需要更换 onnxruntime 发行版，已列为 Non-Goal。

### D8：仅对特定后端有效的参数不得在其他后端下可编辑

`ultralytics_device`、`ultralytics_half`、`ultralytics_tracker`、`ultralytics_track_persist` 只在 `.pt` 模型走 Ultralytics 路径时生效；使用 `.onnx` 模型时 `OnnxObbProcessor` 完全不读取它们。同理，ONNX 路径产出的检测结果 `track_id` 恒为空，`show_track_id_overlay` 无论开关都不会显示出跟踪 ID。现场调整这些项不会产生任何效果，属于误导。

**决定**：按当前模型格式决定这些参数在配置页是否可编辑，不可编辑时给出原因说明。配置值本身保留不清空，以便切回 `.pt` 模型时恢复原设置。

同时移除 `CameraWorker.frame_ready` —— 该信号已定义并被连接，但从未 emit，属于死代码。

### D9：分段耗时必须可观测

当前只有一个合计的 `latency_ms`，且在模板门控下它把匹配与 YOLO 混在一起，无法判断瓶颈。本次优化完成后周期仍可能不达标，届时若没有分段数据，只能回到开发侧盲猜。更换低像素相机后各段占比还会显著变化，更需要现场能自行读数。

**决定**：把模板匹配耗时、YOLO 推理耗时、界面渲染耗时分别上报到管线统计。`ShapeMatchResult` 已带 `total_ms`/`coarse_ms`/`refine_ms`，门控处理器据此填充，无需新增测量点。

## Risks / Trade-offs

- **渲染与判定解耦后，两者的推进节奏不再一致** → 判定仍逐事件推进，显示只反映最新状态，这正是预期行为。风险在于界面上的派生状态（识别列表、KPI）若也移出事件路径会导致状态滞后。缓解：派生状态更新保留在事件处理路径中，只把画面渲染移出。

- **瞬时积压期间事件负载持有整帧快照，内存会上升** → 缓解：解耦后事件处理变廉价，积压窗口很短；若实测仍有持续积压，再单独评估负载瘦身，而不是在本次盲目改动同帧证据的取帧方式。

- **模板匹配涉及数值路径，优化可能悄悄改变判定** → 缓解：以固定图像与模板的等价性测试兜底，断言得分差 `< 1e-6` 且位姿与结论完全一致；等价性测试失败即视为该项优化不可接受，而非放宽阈值。

- **取消采集拷贝后，预览与推理共享同一数组，任何一处原地修改都会污染另一处** → 缓解：把“只读”作为规格约束写明，保留 getter 的副本语义，并保留推理线程交付界面前的那次拷贝。

- **渲染守卫若键选取不当会导致该刷新时不刷新** → 缓解：键包含控件尺寸以覆盖窗口缩放；预览与检测分别取各自的帧编号来源，帧编号变化时立即渲染。

- **画面停在最后一次推理帧会被误读为程序卡死** → 缓解：状态区保持“检测中”指示，并让分段耗时与推理帧率在界面可见，使停顿可被解释。

- **本次不动降采样插值方式，若现场存在小目标漏检则问题依旧** → 这是有意的范围切分：该改动会改变检测结果，必须与精度验证一起评估。已在 Non-Goals 中记录，待更换低像素相机后重新评估。

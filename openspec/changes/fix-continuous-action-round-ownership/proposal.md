# 修复连续动作识别的轮次归属

## Why

现场日志显示：识别本身没有漏检，轮次归属错了。

- 现场共生成 20 个动作事件：包装 10 个、封装 10 个，全部 `missing=-`，即每件产品的组成件在模型侧都已识别完整。
- 业务侧对这 20 个事件的裁决为：通过 12 个、拒收 5 个（包装 3 个、封装 2 个，原因均为 `before_round_start`）、错序 NG 3 个。
- 已结束 7 轮，结果为 5 PASS、2 NG；第 8 轮处于包装 `waiting`、封装 NG 的状态，且 `round` 仍为 `in_progress`。

拒收和错序都发生在同一时刻的边界上：上一轮动作结束与下一件产品开始几乎重合，而新轮的起始门槛取的是"延迟 UI 时刻的最新预览帧"，于是本应属于下一轮的动作事件被判定为"轮次尚未开始"而拒收，紧随其后的配对动作则被判成错序。

具体证据（`live_log_diagnosis.json`，来源 `lstm_workbench/logs/action_trace.log`）：

| 位置 | 现场现象 |
|---|---|
| 第 1 轮 | 10:46:39.202 结束；同一时刻下一件包装从第 103 帧开始 |
| 第 2 轮起点 | 10:46:40.216 建立，起始门槛为第 109 帧，晚于 103 |
| 包装 103–150 | 10:46:47.736 生成后被拒收（`before_round_start`） |
| 封装 150–170 | 紧随其后被判错序 NG |
| 封装 215–250 | 新轮门槛 221，事件被拒收 |
| 包装 328–380 | 新轮门槛 334，事件被拒收 |
| 封装 441–481 | 新轮门槛 448，事件被拒收 |
| 包装 810–854 | 新轮门槛 816，事件被拒收 |

现场换轮耗时约 1 秒，`confirm_frames=1`，因此这不是"旧的 5 秒确认窗口"配置造成的滞后，而是轮次起点取帧口径与动作事件归属口径不一致。

复现与对照（事件层，未运行相机、未重新识别视频）：

- **基线重放**：保持 20 个事件不变，调用实际 `StepSequenceEngine` 重放，结果与现场 20 个决定完全一致（同一事件、同一结果、同一原因），说明重放模型可信。
- **隔离对照**：仅把新轮事件的起点门槛改为"已结束前轮的该动作半开结束边界"，保留 `(session, event)` 去重，20 个事件全部 `expected_step` 通过，10 轮全部 PASS。
- **对照的边界**：该对照只证明"归属口径"是根因，没有验证相机、真实 Qt 定时器，也没有覆盖错误/缺件场景，不能据此推断现场一定 10 轮通过。

本条修复不涉及模型准确率：不重训，不改 YOLO 阈值或权重。

## What Changes

1. **动作事件按业务边界归属轮次，而不是按延迟 UI 时刻的最新预览帧归属。** 事件携带的是它自身采样到的源帧区间；轮次判定应使用该事件所属产品的业务起点（含前轮动作的半开结束边界）判断是否"在新轮开始之后"，不再用事件被消费时界面上的最新预览帧反推。
2. **LSTM 模式的结果展示间隔与事件消费解耦。** 展示节流只控制 UI 刷新，不得阻塞或丢弃下一轮事件；冷却窗口内到达的动作仍要进入轮次判定，不能因为"还没到展示时刻"而丢失。
3. **同一 `(session, event)` 只消费一次。** 去重键沿用现有 `(session, event)` 语义；旧轮事件和重放事件仍然拒收；硬重置切换 session 后不得沿用旧 session 的边界或已消费记录。
4. **真正的错序与缺件必须保持 NG。** 归属修复不能让错误动作通过；在可识别的产品起点恢复轮次状态，不允许"拿下一件包装补上一件漏步"从而把两件产品串成一件事。
5. **异常恢复策略必须在 design 阶段明确写入，并给出可验收的判定条件。** 本提案不承诺"自动超时判 PASS"；任何超时/恢复行为都不能引入未经验证的新配置项。
6. **保留原始证据。** 动作事件、拒收原因、轮次结果的日志字段和输出不得删减或改写，便于修后对拍。

明确不做：不重训模型，不改 YOLO 阈值/权重，不影响 ROI 处理，不影响非 LSTM 模式，不新增未经验证的超时配置。

## Capabilities

### New Capabilities

- `continuous-action-round-ownership`：连续生产场景下，动作事件到轮次的归属规则。要求事件按其业务帧边界归属轮次；轮次起点以前轮动作的半开结束边界为界；同一 `(session, event)` 只消费一次；旧轮与重放事件拒收；session 硬切换时边界与去重状态一并重置；真实错序/缺件仍判 NG 且不得跨产品补步；展示节流与事件消费解耦。

本提案阶段仅建立能力条目与意图级要求，正式的 `specs/continuous-action-round-ownership/spec.md` 规格增量在本变更的后续阶段补齐（本次工作单只允许新建 proposal.md）。

### Modified Capabilities

- 无。现有已归档主规格中不存在轮次归属相关能力；早先的 `streaming-lstm-actions` 与 `action-sequence-part-gate` 仅存在于**未归档**变更 `integrate-lstm-sequence-runtime` 中，本提案只在其之上补充归属规则，衔接关系见 Impact；不修改该历史变更的任何文件。

## Impact

**代码**

- `src/ui/main_window.py`：LSTM 模式下结果展示节流与事件消费的调用关系；轮次/会话状态与 UI 定时器解耦。
- `src/step_sequence/step_sequence_engine.py`：轮次起点门槛的取帧口径（业务边界 vs 最新预览帧）、`(session, event)` 去重、旧轮/重放事件拒收、错序与缺件判定、产品起点恢复。
- `src/lstm_action/stream.py`：仅在边界/状态上报确有必要时调整（源帧区间、会话标识、事件序号的完整性），不做与本问题无关的重构。
- `tests/`：新增/扩充事件层对拍测试——用现场 20 个事件复现基线 12 pass / 5 reject / 3 NG；验证边界对照下 10 轮 PASS；补充同 `(session, event)` 重放、session 硬切换、真实错序、缺件不得 PASS 的用例。

**文档**

- 中文文档：LSTM 模式轮次归属规则、异常恢复策略、修后对拍方法与结果记录位置。

**行为与风险**

- 变更只作用于 LSTM 模式的轮次归属；非 LSTM 模式与 ROI 处理路径保持原行为。
- 轮次归属语义变化会改变部分历史事件的结果（原先 rejected 的事件会进入下一轮），需以事件日志对拍作为验收依据，不能只看 UI 最终显示。
- 未覆盖：相机实时链路、真实 Qt 定时器时序、错误/缺件现场组合场景；这些必须在实施后的现场或可复现环境中另行验证。
- 保留原始动作事件、拒收原因与轮次结果日志，作为回归基线。
